# Заметки по этапам (для отчётов по практике)

## Этап 0. Окружение и репозиторий

- Сделано: проверены Python 3.14 и Git 2.55; установлен PostgreSQL 18 через winget, созданы пользователь и база `bugtracker` (UTF-8); создан Git-репозиторий, виртуальное окружение venv, `.gitignore`, `.env.example`; SQL-схема БД сохранена в `schema.sql` (добавлен статус rejected).
- Сложности: установщик PostgreSQL не добавляет `psql` в PATH, добавляли вручную; из-за разных кодировок консоли (866) и psql (1251) русское имя роли сохранилось «кракозябрами», решение — `chcp 1251` перед запуском psql.
- Инструменты: PowerShell, winget, psql, git (`status`, `check-ignore`, `log --stat`), парсер SQL pglast для проверки синтаксиса `schema.sql`.

## Этап 1. Каркас Flask-приложения

- Сделано: установлены Flask и python-dotenv (`requirements.txt`); настройки вынесены в `config.py` и читаются из `.env`; фабрика `create_app()` подключает 4 модуля (blueprints) — projects (`/`), auth (`/auth`), bugs (`/bugs`), admin (`/admin`); базовый шаблон `base.html` с меню, страницы-заглушки наследуют его, простой CSS.
- Сложности: циклический импорт между `__init__.py` и `routes.py` blueprint'а — решён импортом маршрутов в конце файла; русский текст в выводе консоли Windows отображается «кракозябрами» (кодировка консоли), на работу приложения не влияет.
- Инструменты: `flask run` в режиме отладки (автоперезапуск, отладчик в браузере, лог запросов в консоли), `flask routes` для проверки карты адресов, тестовый клиент Flask (`app.test_client()`) для проверки ответов страниц.

## Этап 2. Модели и миграции

- Сделано: подключены Flask-SQLAlchemy, Flask-Migrate и драйвер psycopg; в `app/models.py` описаны 7 таблиц (модели Role, User, Project, Bug, Comment, StatusHistory и связующая таблица project_members) с CHECK-ограничениями, внешними ключами, каскадным удалением и индексами; первая миграция создаёт все таблицы, вторая (миграция с данными) — роли admin/tester/developer.
- Решения по схеме: пересмотрели NULL — NOT NULL везде, где пустое значение бессмысленно (severity, priority с DEFAULT 'medium', updated_by, created_by, old_status, changed_by); nullable оставлены только описание, шаги, ожидаемый/фактический результат, окружение и исполнитель.
- Сложности: при откате и повторном применении миграции id ролей стали 4–6 — счётчик SERIAL не сбрасывается, поэтому роли в коде ищем по имени, а не по id.
- Инструменты: `flask db migrate/upgrade/downgrade/history/current`, ручная проверка сгенерированной миграции перед применением, проверка ограничений тестовыми INSERT в откатываемой транзакции, `flask shell`, psql (`\dt`, `\d bugs`).

## Этап 3. Авторизация и роли

- Сделано: пароли хранятся только как хэш (scrypt с солью, werkzeug); вход и выход через Flask-Login; формы входа и регистрации на Flask-WTF с русскими сообщениями и проверкой уникальности логина и почты; регистрация создаёт заблокированный аккаунт, который одобряет админ; заблокированный не может войти, а уже вошедшего выкидывает при следующем запросе; декоратор `role_required` (403 для чужой роли), админка только для admin; команда `flask create-admin`.
- Безопасность: CSRFProtect для всего приложения, выход только через POST с CSRF-токеном; сообщение о блокировке только после верного пароля; при ошибке — общее «Неверный логин или пароль»; защита от open redirect в параметре `next` (проверка из туториала через `urlsplit` пропускала `/\evil.com`, заменена своей).
- Сложности: проверка входа сначала «падала» — вошедшего перекидывало на вход. Причина была в самой проверке: запросы шли внутри одного общего контекста приложения, и Flask-Login брал «гостя» из кэша `g` предыдущего запроса. Нашли, распечатав содержимое сессии; в тестах каждый запрос должен идти в своём контексте.
- Инструменты: тестовый клиент Flask с настоящими POST-запросами и CSRF-токеном, `session_transaction()` для просмотра сессии, `test_cli_runner()` для проверки консольной команды, `flask routes` для проверки методов маршрутов.

## Этап 4. Проекты и участники

- Сделано: список проектов с учётом роли (админ видит все, остальные — только свои); создание и редактирование проекта (только admin, уникальность названия с учётом редактируемого проекта); страница проекта с участниками; добавление и удаление участников (только admin, POST с CSRF); общая проверка доступа `get_project_or_403` (нет проекта — 404, не участник — 403) для будущих страниц багов. По ходу этапа ТЗ дополнено редактированием проекта; удаление проекта сознательно не делаем — вместе с ним удалились бы баги.
- Безопасность: список пользователей для добавления формируется на сервере, SelectField отклоняет подменённый id (заблокированный, админ, уже участник); вывод через Jinja экранируется — `<script>` в описании показывается текстом (защита от XSS).
- Сложности: в проверках дважды получили 400 вместо ожидаемого 403 — CSRF-токен брался из другой сессии тестового клиента, и срабатывала CSRF-защита раньше проверки роли; с токеном той же сессии получили правильный 403. Вывод для тестов: токен брать тем же клиентом, что отправляет запрос.
- Инструменты: тестовый клиент Flask (проверки доступа для каждой роли, подмена данных формы), регулярные выражения для разбора HTML в проверках, `flask routes` (изменяющие маршруты — только POST).

## Этап 5. Баги: CRUD

- Сделано: создание бага (tester — участник проекта; серьёзность обязательна, приоритет по умолчанию medium); карточка бага с доступом как к проекту; списки багов на странице проекта и в разделе «Баги» (админ видит все); редактирование (только автор и admin, статус формой не меняется — подменённый `status` в запросе игнорируется); назначение исполнителя: автор и admin выбирают активного developer-участника, developer берёт свободный баг себе и может отказаться.
- Правила уточнены вместе с ТЗ и записаны в ТЗ: баг в работе без исполнителя возвращается в new (от имени того, кто снял назначение); при удалении участника из проекта с него снимаются назначения в этом проекте. Общие правила назначения вынесены в `app/assignments.py`, чтобы использовать их и при блокировке пользователя (этап 8).
- Сложности: макрос таблицы багов падал с `UndefinedError: 'STATUS_LABELS' is undefined` — Jinja импортирует макросы без контекста шаблона; исправлено `import ... with context`. В одной проверке объект проекта удалялся сборщиком мусора до записи изменения (ошибка в скрипте проверки, не в приложении).
- Инструменты: тестовый клиент Flask с проверкой каждой роли и подменой данных форм (чужой id, лишнее поле status), трассировка ошибки Jinja в логе Flask, повторный прогон прежних проверок после каждого изменения (регрессия).
